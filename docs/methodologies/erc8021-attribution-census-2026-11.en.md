- Question: on USDC settlements submitted by CDP-labelled signers on Base, how often does the calldata end with an ERC-8021 attribution suffix, which codes does it carry, and how many receivers (`payTo`) do those codes cover?
- Spec reference (immovable version): x402-foundation/x402 `docs/extensions/builder-code.mdx` @ `10b2d06b9472` (2026-10-06). Fields: `a` = app code, set by the resource server; `w` = wallet code, set by the facilitator; `s` = service code(s), any party; `m` = settlement metadata, facilitator only. The facilitator reads `a` and `s` from the payment payload, adds `w`, appends a Schema 2 CBOR suffix; a client must not set `a` unless the server declared the extension; "On v1 payloads, `a` is omitted from the suffix" (line 415). Reference implementation; a production facilitator may differ.
- Origin: our own two settlements of 2026-11-06, both submitted through CDP's facilitator, end with `{w: "cdp_facil1"}` and no `a`; neither of our servers declared the builder-code extension at the time, so no `a` was expected. The census asks how everyone else compares.
- First authors with published decodings (used as the outside check of the parser): sukrutkrdg (x402-foundation/x402 #3045, comment 5397445138) and MikeyPetrillo (#2704).
- Codes: attribution codes are printed in this public version as labels (code T, code T2, code R and so on), not as the strings found on chain. A label is not a quotation of the code.

## What this measures

"Attribution landed on chain": whether a settlement's calldata ends with the ERC-8021 marker (16 bytes `0x8021` × 8), the schema id before it, and for Schema 2 the CBOR map (Schema 0: ASCII code list). Unit = settlement transaction (DISTINCT `tx_hash`) in the transaction sections; unit = receiver address (`payTo`) in the receiver section. Neither is a business: one business can use many `payTo`, one `payTo` can serve many hosts.

It does not measure:
- what a resource server declares in its 402 response (the on-chain end only);
- why `a` is missing: no declaration, no echo by the buyer's client, v1 payload, or a facilitator that dropped it are indistinguishable in calldata;
- who wrote a code: the instrument sees the result, not the author (a facilitator or an SDK could insert a default `a`);
- whether a code belongs to the business it suggests: codes are self-declared; "code X" is not "company X". No labels for businesses.

## Two routes

Route L (ledger → calldata). Ledger rows on Base, 0.0005–5 USDC, window by `block_number` (bounds from RPC; `timestamp` is the tracker WRITE time, used only as a coarse index range with −1 h / +8 h margins; 0 rows with a block in the window were written after the margin, checked over the next 48 h for W7 and until 8 Nov ~22:3xZ (~14 h) for D1). Population = facilitator-mediated settlements (`tx_sender ≠ from_wallet`, sender with ≥ 1,000 distinct payers in W7). Strata: CDP (20 qualifying signers); top-10 other qualifying senders; the rest; negative control = direct transfers. Deterministic bottom-k sample `ORDER BY substr(tx_hash, 31, 16)` (uniform hash bytes → simple random sample without replacement): 400 CDP, 120 per top-10 sender, 240 rest, 50 negative. Calldata by hash from public RPC. D1 reuses the W7 facilitator set (the ≥ 1,000-payer rule depends on window length: one day alone qualifies 3 senders, 0 of them CDP). Intervals: Wilson 95 %.

Route C (chain only). Random blocks (seed 20261108, W7: 150 blocks; 20261109, D1: 1,600 blocks, after the 2 s → 0.2 s block-time switch of 5 Nov), every transaction to USDC with one of four EIP-3009 selectors (`0xe3ee160e`, `0xcf092995`, `0xef55bec6`, `0x88b7ab63`). Mediated = `tx.from ≠ authorization.from`; CDP = `tx.from` in the same 69-address list (independent of `w`). `payTo` kept only as a 10-character hash. Intervals: bootstrap over blocks (cluster sample; seed 1, 1,000 resamples); one-sided rule-of-three bounds at 0 % / 100 %.

Windows (bounds re-read by RPC): W7 = blocks 53,178,127–53,480,526 (Wed 2026-10-28T00:00:01Z → Wed 2026-11-04T00:00:01Z, i.e. Wed–Tue; before the period of 5–6 Nov in which ledger rows were written without a recorded sending address). D1 = blocks 54,096,122–54,528,121 (Sat 2026-11-07T00:00:00Z → 2026-11-08T00:00:00Z).

## Start of CDP's suffix

- CDP's direct EIP-3009 settlements began carrying `w = cdp_facil1` on 11 June 2026 between 22:37:33Z and 22:42:03Z. Block probes by the review: 0/149 suffixed in 13 blocks before, one block at 22:39:47Z mixed (5/10; within one signer 3 of 4), 14/14 in 3 blocks after; the author re-checked the three blocks around the switch by RPC (0/6, 5/10, 6/6). Consistent with a rolling switch; mechanism not established. 13 probed blocks are ~26 s of chain time: they rule out "on for all traffic" at those moments, not an earlier low-rate canary; the back series (44/44 without a suffix 1–11 June) is the complementary evidence. `w` is what switched on; `a` appears in the series only from July.
- Public anchor (context only): CDP's changelog lists "Attribution (Builder Codes)" under June 19, 2026 (docs.cdp.coinbase.com/get-started/changelog, raw markdown l. 125 date, l. 133 entry; read 2026-11-10), 8 days after the measured switch. No inference about CDP's rollout process from this.
- Back series (633 samples, ~4/day from 1 June; first CDP row of each hourly write batch, always a full-hour block): last without suffix block 47,203,928 (11 June 17:00:03Z), first with suffix 47,214,728 (11 June 23:00:03Z), then 589/589. It over-represents hourly automata (one hourly automaton's code 201/589 in the series vs 0/957 in the uniform W7 samples) → date only, never code shares.

## Traps caught during the measurement

1. A filter on the chain column let the SQLite query optimiser pick the table's automatic index on `chain` = a full ledger scan (stopped at 9.1 GB) → `INDEXED BY idx_timestamp` + `EXPLAIN QUERY PLAN` before every heavier read.
2. The ≥ 1,000-payer threshold depends on window length → D1 uses the W7 set; it also excludes single-app relays by design.
3. The tracker writes hourly batches: write-time windows HH:30–HH:59 are empty → windows by block.
4. Back series = biased selection.
5. The all-layer weighted estimate mixes bundlers into a "facilitator" share.
6. (review) Denominators of the "without the dominant code" share; an unweighted stratified share (8.3 %) had been copied into a related method note; corrected there too.

## What the instrument does not see

- Route C misses CDP's proxy settlements (1.5 % of route-L CDP samples); both routes miss relays with < 1,000 payers that do not call USDC directly, multicall / deploy-then-pay paths from unlisted senders, other tokens, other networks, and non-CDP amounts outside the band.
- The protocol version of the payment payload (v1 drops `a` per spec).
- Why `a` is missing, who wrote a code, whether a code is registered to the business it suggests.
- Limits of this public version: code values are replaced by labels (code T, T2, R), so without them a reader cannot reproduce the claims about specific codes.

## Ways this can be refuted

1. List blind spot and list scope: a CDP signer missing from the facilitator table that appends no `w` would be counted as "other mediated" in route C and invisible to the completeness test (pool-2 itself was found only on 13 Jun from an outside tip); conversely, a listed address can carry band traffic through a contract path other than EIP-3009 on USDC or the settlement contracts, and that traffic enters the population (seen once: 2 transactions in W7, no suffix).
2. Window dependence: one automaton (and in D1 a second) moves the transaction share by 30 points in ten days; one code's receiver share went 12.5 % → 20.0 % (404/3,228 → 178/889; all of D1's in one 2.83-hour burst, W7's spread but 76 % in 03–09Z); weekday vs weekend differs; two windows do not establish a level.
3. Encoding variance: suffixes the parser rejects would count as "no `a`"; the independent decode covers 91 samples with no non-canonical CBOR; an attribution placed anywhere other than the end is invisible by design.
4. Population rule: route L depends on the band and on the ≥ 1,000-payer rule; route C is independent of both but covers only direct EIP-3009 calls on USDC.
5. Receiver census: "has `a`" in up to 3 draws is a lower bound for busy receivers (52 % / 35 % of the listed denominators rest on three draws); the listed flag is one snapshot (tested 2026-11-09: any read inside the window moves W7 listed receivers 1,509 → 1,549 and `a` among listed 4.2 → 4.3 %; code R stays at 0 listed); non-USDC contracts rarely carry `a` (1 of 129 draws), so receivers paid through them may be under-counted.
